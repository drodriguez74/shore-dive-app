# Aesthetic Review — 2026-08-08

A second adversarial review pass, distinct from `plan.md`'s content/domain review — this one covers the actual *visual design, feel, and craft* of the rendered mockups (via `agent-browser` screenshots, not just reading CSS source), from the same five perspectives: product, business, UX craft, working diver, and dive-shop owner. Findings triaged into the same three buckets `plan.md`'s Priority Triage uses: **MVP** (real, verified issues worth fixing), **Optional/Bonus** (real value, not required), and **Blocked** (questions a decision, not a bug — no work happens here without founder sign-off).

## MVP — fixed

- [x] **Safe-Return "Hold to check in — I'm safe" button was low-contrast in light mode** — the single most safety-critical control in the app. Verified two ways: read the source (`hold-to-confirm-button.tsx` had `bg-emerald-950/40` + `text-emerald-100` with no light-mode-specific override, only the border had a `dark:` variant) and confirmed visually — started a real timer via `agent-browser` in forced light mode and screenshotted it: pale mint text on a similarly pale background, legible but visibly weak. **Fixed:** explicit light-mode colors (`bg-emerald-50 text-emerald-900`) separate from the dark-mode values, same fix applied to the `danger`/rose variant for consistency. Re-verified visually — now dark, bold, clearly legible.
- [x] **The `SecurityGapNotice` on `/moderation/camera-sources` read like a leaked engineering ticket** — found independently by both the dive-shop and business aesthetic reviews (same screen, same complaint, arrived at separately). The real component had raw file paths (`0002_rls.sql`, `supabase/README.md`, a full route path) inline in user-facing copy. **Fixed:** kept the disclosure exactly as honest (any signed-in user can act, no moderator role yet, will be tightened before launch), moved the technical cross-references into a code comment where they belong, rewrote the user-facing copy in plain language.

## MVP — real, verified, not yet fixed (needs real design/engineering work, not a quick patch)

- **Map pin system doesn't pass a glance test** — flagged independently by both the diver review (colorblind risk, glare-prone amber/rose hues, needs a legend tooltip to be understood at all) and the UX craft review (ring-vs-fill hue distinction hard to read at a 30×38px pin against dark navy). This isn't a quick color tweak — it's a real encoding-legibility problem in the three-axis system (ring=provenance, fill=hazard, glyph=legal-status). Since the map isn't wired to real data yet anyway (`plan.md`'s Task 11.5, the biggest MVP item from the content review), **fix this as part of that same build**, not in isolation on mockups nobody's shipping yet.
- **Dead-space/empty-viewport on 5 mockup screens** across 4 flows (permission-denied, checked-in confirmation, prefetch-idle/fetching, offline-nothing-cached) — content ends ~40-45% down the viewport with nothing below it, reads as broken rather than intentional whitespace. Mechanical fix (vertically center, extend the card, or add a persistent footer), but these mockups aren't live app code yet (only Safe-Return is) — apply this fix when each flow actually gets built, and hold the mockups themselves as the reference for what "should" look like once that happens.

## Optional / Bonus — real value, confirmed not required

- No shared component tokens across the 38 mockups (button border-radius spans 4px-32px, min-height spans 44-58px depending on file) — invisible to users, matters once a real component library gets built from these mockups (`/design-sync`).
- One color-system violation: `lds-moderation/02-submission-form.html`'s "Submit report" button is solid violet (should be `sky`, matching every other primary CTA) — low-traffic mockup, not urgent.
- Dive Gradient applied to two different roles (logo mark vs. user avatar) depending on flow — needs one explicit decision, not urgent.
- Onboarding hero logo mark underwhelms against its own gradient background; site-detail's hero is a placeholder wave icon, not a real photo slot — polish items.
- Dive-shop visual parity: a shop's fill-station pin renders as a 14px flat dot vs. a 30×38px shadowed teardrop for a dive site; no logo/photo/hours slot in the shop listing card. Ties to the already-deferred "no shop value exchange" finding from the content review — same bucket, deferred until real shop outreach.
- Component consistency is otherwise genuinely strong (badges, bottom sheets, warning-box patterns all recur correctly); state-family design (Safe-Return's 5 states, offline-prefetch's 4 states) is the strongest work in the whole set — nothing to fix, noted so it doesn't get accidentally "improved" into something worse.

## Blocked — these question the design system's premises, not bugs; no work happens without a founder decision

- **"Dark UI reads better in outdoor sunlight" — directly disputed by the diver review** on real-world grounds (a dark screen in direct sun can glare/mirror as badly as a light one). This is foundational to `DESIGN_SYSTEM.md` §1's entire dark-first rationale — reworking it would ripple through all 38 mockups. Needs explicit founder judgment before any rework, not a unilateral change.
- **"Built by one person, hobby project, no revenue" sits directly at the OAuth trust moment** (welcome screen, sign-in screen) — in tension with this project's own honesty-first ethos (`CLAUDE.md` explicitly wants solo/hobby status disclosed). Softening it for trust vs. keeping it for transparency is a founder call.
- **"Reads as generic dark SaaS, not diver-authentic"** (diver review — strip the copy and nothing visual says "diving"; the same gradient/pins/alarm-bell iconography would work unchanged on a fintech app) — a real direction question (custom illustration/photography investment vs. the current abstract palette-driven look), which is a resourcing decision, not a quick fix.

## Method note

All five reviews rendered actual mockup HTML via `agent-browser` (not just read CSS source) and screenshotted what they saw before critiquing. The two MVP fixes above were independently re-verified by reading the real source AND visually confirming against the real, live app (not the mockups) before and after the fix — same rigor as every other change this session. Full per-screen findings and ~90 screenshots from all five reviews existed only in this session's scratchpad and were not preserved beyond the two write-ups above; re-run the review if the underlying rationale needs to be revisited in more depth than this summary carries.
