## Product

Shore-Diving Intelligence & Discovery Platform — a **100% free-to-use, zero-monetization** installable web app for discovering and safely diving hyper-local *shore* sites. "Free" describes the user-facing core product, not infra cost — see `plan.md`'s Funding & Cost Model for how infra-heavy features are actually paid for. Success is measured by safety adoption and hyper-local discovery, **not** engagement metrics; avoid noisy/growth-hacky patterns (e.g. push spam). Four product pillars (source of truth: `plan.md`):

- **Map-Driven Exploration** — a clean, low-noise interactive map with dynamic color-coded telemetry pins to surface hidden shore-dive gems. Pins default to **exact coordinates** (no geofuzzing) — shore sites are on public, walkable coastline and are rarely genuinely secret, so hiding coordinates doesn't protect anything real. The one real, distinct concern is legal/access restrictions (marine protected areas, seasonal closures, private property) — surface those as an explicit access/legal-status badge on the pin. Every pin also carries a two-state provenance tag (`VERIFIED` / `COMMUNITY`) — never render a bare color pin with no lineage.
- **Intent-Driven Offline Cache** — pre-bundle site telemetry, hazard maps, and visual assets ~24h before a planned dive window so sites are usable with **zero cellular coverage** at the water's edge. Treat the network as unreliable/absent by default; offline is the primary case, not a fallback. On the web this means the Serwist service worker precaching/runtime-caching static assets, plus structured site/hazard data cached in IndexedDB — not a native background-fetch API. Prefetch is **best-effort, not guaranteed** (a service worker only updates its cache when the site is actually opened, or via periodic background sync where the browser supports it) — always pair it with a manual "Prefetch Now" path, and show freshness ("as of [time]"), not just a binary cached badge.
- **Frictionless Voice Logging** — post-dive audio capture converted into structured logbook entries (max depth, runtime, marine life, conditions). On-device/in-browser STT is the goal (free, no server round-trip), but browser Speech Recognition support is inconsistent — notably weak/absent on iOS Safari — so this needs a graceful degraded path (manual entry) rather than assuming it always works. Transcribed fields require a confirm/edit step before saving — never auto-commit.
- **Safety first, v1 scope is local-only, reliability is honestly disclosed** — the Safe-Return timer in v1 is an on-device countdown with an alarm fallback; it does **not** notify anyone remotely (no budget for SMS, no verified contact list yet). On the web, background execution and notifications are unreliable once the tab/PWA isn't in the foreground — **especially on iOS Safari**, which has no flashlight/torch API and only supports installed-PWA notifications on 16.4+. The founder's explicit decision: **accept this for v1 and disclose it clearly** rather than block on a native wrapper. The UI must never imply a guarantee ("help is coming," "you'll be notified") the platform can't back — say plainly that reliability is best when the app stays open and is weaker on iPhone. Any hazard/visibility data feeding a diver's go/no-go decision is also life-safety-critical and held to the same correctness bar.

## Stack

- **Next.js (App Router)** + **TypeScript** + **Tailwind**, hosted on **Vercel**. This is a PWA — installable, but the website *is* the app, no native build.
- **PWA layer: Serwist** (`@serwist/next`) — service worker precaching + runtime caching, configured in `next.config.ts` (`swSrc: src/app/sw.ts`, generates `public/sw.js`, gitignored) and `src/app/manifest.ts`. **Serwist doesn't support Turbopack yet** — `dev`/`build` scripts explicitly pass `--webpack` in `package.json`; don't remove that flag without confirming Serwist's Turbopack support has landed (`@serwist/next` will warn loudly if you do).
- **Backend/data platform: Supabase** — Postgres (provenance-tagged pin/hazard/LDS data), Supabase Auth (**Google sign-in only**, P0-A — Apple dropped, requires a paid $99/yr Developer Program membership with no free path), Supabase Storage (offline bundle assets for Task 12). Client helper at `src/lib/supabase.ts`; throws at import time if env vars are missing, so don't import it from a module that might load without `.env.local` configured.
- **Map provider: Mapbox** via `mapbox-gl` + `react-map-gl` (`react-map-gl/mapbox` import path). Web-native, no custom native build needed — this is one of the things that got easier after the platform pivot. Component: `src/components/site-map.tsx`.
- **Structured offline data:** IndexedDB is the intended store for structured cached records (site/hazard/pin data with freshness timestamps, Task 12/13) — no wrapper library installed yet; a lightweight one (e.g. Dexie.js) is the natural next step when Task 12 starts, chosen for TypeScript ergonomics over raw IndexedDB, not yet confirmed with the founder.
- Remaining libraries (audio capture/STT for voice logging, Web Push for a future connected Safe-Return channel) are chosen per-feature as the app is built — record each choice here once made so future work stays consistent.

## Architecture

Feature modules map directly to the `plan.md` task backlog. **Phase 0 (auth/identity, the provenance/trust-tier model, and PII classification) must exist before Phase 1 features are built on top of it** — these are foundation, not backlog items to fit in later. When implementing, keep each concern isolated so batches stay small and reviewable:

- **Phase 0 prerequisites** (P0-A/B/C) — **Sign in with Google only** via Supabase Auth's web OAuth redirect flow (no phone number, no SMS dependency; Apple dropped for cost — see Stack section); a **two-state** pin/hazard/LDS provenance model (`VERIFIED` / `COMMUNITY`) in Postgres, simplified from an earlier four-tier design — expand later once there's more than one contributor; encryption-at-rest + minimal-retention policy for PII, which in v1 is just account identity, dive-plan location, and timer state (no emergency contacts yet).
- **Offline prefetch pipeline** (Task 12) — best-effort caching (Serwist service worker for assets, IndexedDB for structured data) triggered when a site is added to an active dive plan and reinforced ~24h before the dive window, backed by a manual "Prefetch Now" trigger since there's no guaranteed background execution on the web. Cached bundles are integrity-checked (signed/checksummed) before being marked ready — fail closed on a bad check.
- **Offline sync status UI** (Task 13) — freshness indicators ("cached as of [time]", staleness-warned past a threshold), not a binary pre-cached badge.
- **Post-dive micro-prompt engine** (Task 14) — single-tap condition-logging workflow, gated on conservative trigger conditions (active dive-plan check-in state) to avoid false-positive prompts.
- **Safe-Return emergency timer** (Task 15) — **v1 is local-only and web-constrained**: an on-device countdown with an alarm fallback on expiry (Notification API + Web Audio + Vibration API where supported). No emergency-contact list, no push, no SMS in v1 — deliberate, not an oversight. Check-in requires re-authentication/confirmation, not a passive dismiss. Onboarding must state plainly that this doesn't notify anyone else, **and that reliability depends on the app staying open, especially on iPhone** (see Product pillar above and `THREAT_MODEL.md`). **Life-safety-critical**: correctness and honest failure disclosure matter more here than anywhere else in the backlog, even in this reduced, web-constrained scope. A connected alert channel (Web Push, then SMS) is a deliberately deferred future phase, not part of this task.
- **Local Dive Shop (LDS) logistics layer** (Task 16) — map integrations + status feeds for nearby fill stations and emergency gear, using the two-state provenance model + last-verified-timestamp treatment as hazard data.
- **Webcam / visual intelligence** (Tasks 17–20) — feeds sourced only from an **allowlist/partnership model** (municipal open-data, opted-in dive shops), never indiscriminate scraping; a vision-model worker bounded to **free/cheap-tier APIs only** with a hard call-volume cap, output always tagged `MODEL_INFERRED` with a confidence score and rendered visually distinct from verified data; a discovery agent whose output lands in a human-review moderation queue rather than auto-publishing new sources; and a unified media embed component (live stream → embedded player → refreshing stills) that sandboxes any third-party embedded player (iframe `sandbox` attribute, no shared app-auth session/cookies, domain allowlist).

For AI-backed workers (visibility/chop extraction, webcam discovery), default to the latest Claude models — see the `claude-api` skill for current model IDs and usage before wiring these up.

## Engineering standards

`plan.md` frames the near-term work as clearing a **~170-story backlog of refactoring, structured logging, and exception-handling** stories via **modular batch execution**. Hold this bar on every change:

- **Batch discipline** — one story = one small, self-contained, reviewable change. Don't bundle unrelated refactors.
- **Exception handling** — wrap every I/O and browser-API boundary (network/fetch, IndexedDB, Geolocation, camera, microphone, Notification/Push, service worker messaging). Because offline is the default, network failures are an expected code path, not an edge case — handle them explicitly rather than letting them throw.
- **Structured logging** — use a consistent structured logger, not ad-hoc `console.log`, on production paths; log at boundaries with enough context to debug field failures (many will happen offline, at remote sites, after the fact).
- **Safety-critical code** — the Safe-Return timer and offline-cache correctness are the two areas where a bug has real-world consequences; treat them accordingly. Never let a UI imply a guarantee the system can't back (e.g. "help is coming", "fully up to date", "you'll be notified") when it can't be certain — this matters even more now that background reliability is platform-dependent (see Product pillar above).
- **No unmoderated write path to provenance-tagged data** — any code path that lets a pin, hazard status, or LDS status change must go through the `VERIFIED`/`COMMUNITY` provenance model (P0-B), never a direct unmoderated write, even for internal tooling.
- **PII handling** — v1's PII surface is account identity (via Google), dive-plan location, and timer state (P0-C) — no emergency contacts yet. Encrypt at rest/in transit, keep retention minimal, never expose beyond the account owner. Re-scope this when a connected alert channel and emergency contacts are added (see `THREAT_MODEL.md` §11).
- **No paid dependency without checking the funding model** — this is a no-budget solo project; any new SDK/API/service must fit a free or negligible-cost tier, or be flagged to the founder before use.
- **Don't lint or commit generated output** — `public/sw.js` is rebuilt by Serwist on every build; it's excluded from ESLint and gitignored. If you see it in a diff, something's misconfigured.
