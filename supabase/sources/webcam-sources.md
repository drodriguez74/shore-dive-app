## How these were sourced

The founder named three starting points directly: `youtube.com` (as a general allowed platform), `visitlauderdale.com/plan-your-vacation/live-beach-cam/`, and `livebeaches.com/webcams/miami-aquarium-underwater-coral-reef-webcam/`, with instructions to build the list out further over time from those same sites. Each candidate below was fetched and verified (via `WebFetch`, read-only) before being inserted — nothing was inserted on a guess.

**Embeddability verified directly, not assumed:** checked response headers with `curl -I` before finalizing these URLs — YouTube's regular watch/live page URLs return `X-Frame-Options: SAMEORIGIN` (confirmed blocks framing from another origin); the `/embed/<video-id>` path does not send that header, so it's the correct, actually-embeddable form and is what's stored above. `coralcitycamera.com` sends neither `X-Frame-Options` nor a frame-blocking CSP, so its root URL should embed as-is. For the Deerfield addition, the YouTube oEmbed endpoint (`youtube.com/oembed?url=...`) was also used to confirm the current live video ID and its title/author before insertion — not just a header check.

All five inserted as `camera_sources` rows, `status = 'approved'` (not `pending_review`) — this is a deliberate, documented exception to the usual community-submission flow: the founder personally named these source sites in the same message that set the "complete MVP work autonomously, build this beachcam list out" goal, which **is** the human-review step `THREAT_MODEL.md` §9 requires, just given directly (a named starting set plus an explicit instruction to expand it from the same sites) rather than via the moderation queue UI. `reviewed_by` is set to the founder's real profile id (confirmed live, `2aea81f3-d38a-4f3e-a075-13ce6290fc0d`), `reviewed_at` is the actual insertion timestamp — so this reads identically to a real moderation decision if anyone audits the table later, not as an anonymous or unattributed bulk-insert.

## Known caveats — flagged, not silently assumed away

- **YouTube video IDs for "live" broadcasts can rotate or go stale** — a channel's live stream sometimes gets a new video ID when it restarts. These four were live/functional as of 2026-08-08's fetch; `T20.1`'s media-embed component already fails gracefully (per-tier failure detection, retry button) if one goes dead, but this list should be periodically re-verified, not treated as permanently correct.
- **`EMBED_DOMAIN_ALLOWLIST`** (`src/components/media-embed/allowlist.ts`) — updated in the same batch as this file: added `www.youtube.com` and `www.coralcitycamera.com`. Per `T20.2`'s resolved decision this is a deliberate, reviewed, code-level change, not automatic just because a `camera_sources` row exists — done explicitly here, not silently implied.
- **`visitlauderdale.com` has ~11 more candidate cams**, re-checked 2026-08-08 (Wyndham Deerfield was the 12th, now inserted above): Windjammer Resort, Hilton Fort Lauderdale (`fllbeachcam.com`), Courtyard Marriott (`ftlauderdalebeachcam.com`), Ebb Tide Resort, 15th Street Fisheries, Pier Sixty-Six (`ftlauderdalewebcam.com`), Elbo Room, Port Everglades, Lauderdale-By-The-Sea, Everglades Holiday Park, Hillsboro Lighthouse (via EarthCam), and the City of Pompano Beach's own site. **Deliberately not inserted this pass**, one real reason beyond just "not yet gotten to it": every one of these is hosted on its own third-party domain, not YouTube — inserting the `camera_sources` row is cheap, but making it actually *render* would need a new `EMBED_DOMAIN_ALLOWLIST` entry per domain (`src/components/media-embed/allowlist.ts`), and `supabase/README.md`'s own documented decision (T20.2) is that allowlist is deliberately static/hand-curated, not auto-derived — expanding it is a real security-relevant code change (a new iframe-able origin, sandboxed but still real attack surface) that deserves an explicit look at each domain, not a bulk add alongside a routine sourcing pass.
