## Platform Decision (v4, unchanged)

**The app is a Next.js PWA — installable, but also just a website — hosted on Vercel, not a native app.** No App Store fees/review; Mapbox web SDK; Supabase OAuth works over web redirect; trivial Vercel hosting. Cost, accepted deliberately: the Safe-Return timer loses background-execution reliability, especially on iOS Safari (see Resolved Decision 1). Installability (`manifest.ts`) is a convenience, not a trust signal — nothing about "Add to Home Screen" implies app-store-style vetting or safety review; the Safe-Return disclaimer exists partly to compensate for that gap in user expectations, not only for the background-reliability gap.

## Core Architecture & Product Pillars

**Map-Driven Exploration Engine** — a clean, low-noise interactive map with color-coded telemetry pins. No geofuzzing — exact coordinates, since shore-accessible sites aren't genuinely secret. Legal/access restrictions get an explicit badge, not a hidden pin. Every pin carries the two-state provenance tag (P0-B). **v5 additions, from the diver/product review:**
- **This pillar has no live implementation yet** — `sites` is never queried by any app code; the map renders only mock/LDS data. Wiring real site pins is now an explicit task (see Task 11.5).
- Site/hazard data needs structured fields beyond free-text `description`: entry type (beach/surf, rocky scramble, stairs, boat-assist-only), parking notes, typical depth range, typical water temp by season, and — for hazard reports specifically — a `hazard_type` (surge/current, entanglement, boat traffic, sharp bottom, low visibility, other) and, if the founder accepts even a coarse tier, `severity`. Right now "has any hazard report" is the only signal a pin carries, with no age/recency weighting — a 3-week-old minor report and a 2-hour-old dangerous one render identically. Both gaps are scoped into Task 11.5/13.
- **Tide-relative timing is absent entirely**, despite being a bigger factor for *shore* diving specifically (entry/exit access, current, visibility) than almost anything else in this plan — and it's free to add (NOAA tide data, no API cost). At minimum, link the nearest NOAA tide station from site detail.

**Intent-Driven Offline Cache** — best-effort service-worker + IndexedDB caching, manual "Prefetch Now," freshness timestamps not binary badges, signed/checksummed bundles. **v5 status correction:** built (`PrefetchButton`, `PretripChecklist`, bundle signing/verification, the `offline-bundles` Storage bucket) but **not reachable anywhere in the live app** — no route imports either component. This is worse than an unlinked demo page; there's no URL at all. Wiring these into the (not-yet-built) site detail page is part of Task 11.5.

**Frictionless Voice Logging** — post-dive audio capture → structured logbook entry, on-device STT with manual-entry fallback, mandatory confirm/edit before saving (never auto-committed). **v5 field-list correction, from the diver review:** the current scope (max depth, runtime, marine life, conditions) is missing the two fields most standard logbooks and dive computers treat as basic: **tank pressure (start/end — air consumption, the primary self-tracked safety/gear metric after depth/time) and buddy name.** Also worth adding if scope allows: water temp/exposure suit, entry/exit time. Expanded field list: *max depth, runtime, tank pressure (start/end), buddy name, water temp/exposure suit, marine life, conditions.* "Frictionless" describes the *absence of growth-hacky interruptions* (no streaks, no engagement nudges), not the absence of safety/honesty-required friction — permission priming, the confirm/edit gate, and Safe-Return's hold-to-confirm are kept deliberately, even at UX cost, per the Engineering Standards' safety-critical-code section. State this explicitly rather than leaving "frictionless" to read as an unqualified promise.

**Safety first** — Safe-Return timer, v1 local-only, on-device countdown + alarm, no remote alerting (see Resolved Decision 1 for the full, still-current reliability disclosure). **v5 additions:**
- **The timer is silently solo-only.** Diving is a buddy-system activity by default in every major certification curriculum; nothing in the state machine, schema, or disclaimer distinguishes "I checked in" from "we both surfaced," and there's no way to represent a buddy who doesn't carry a phone. This was an unexamined assumption, not a scope decision — resolved as: **v1 stays one-device-per-countdown** (no rebuild), but the disclaimer copy must say so plainly ("this confirms *you* checked in — it does not confirm your buddy did") and the dive-plan label (Task 11.5) should support noting who you're diving with. A real buddy-pair check-in model is a named future task, not silently absent.
- **Add a DAN (Divers Alert Network) reference** to the onboarding/disclaimer copy, alongside "tell a real person your plan" — DAN's emergency hotline is the actual resource trained divers are taught to use in a real dive emergency, not a generic contact. Free (a static link/number), meaningfully upgrades the disclaimer.

**Zero-Monetization Growth Strategy** — 100% free core utility, no budget. **v5 addition:** "free" needs an explicit ceiling for *all* infra this depends on, not only the one feature (webcam AI) Resolved Decision 2 already bounds — see the new Cost Ceiling addendum below.

### 1. Safe-Return timer — v1 is local-only, web-constrained, and disclosed (resolves `THREAT_MODEL.md` §0.1)

It does not notify anyone else, and it's less reliable if you close the app or lock your phone — especially on iPhone. Tell a real person your dive plan before you go."*

**v5 addendum — liability is personal, not institutional, and that's a named risk, not a closed one.** No business entity exists for this project (confirmed: no `author` field, no LLC/incorporation mentioned anywhere) — liability from this feature, or any feature, currently attaches to the founder personally. The in-app disclaimer is a disclosure practice, not a substitute for legal review, and "legal review is not a hard blocker" was a scope/cost decision, not an assessment that the disclaimer is legally sufficient — that distinction wasn't previously stated and should be. Two low-cost mitigations flagged for the founder's explicit yes/no before onboarding real users beyond personal testing: **(1)** cheap/free liability-limiting entity formation (e.g. single-member LLC), **(2)** a one-time consult (a free legal-aid clinic or a lawyer-friend read counts) specifically on whether the current disclaimer/consent flow does anything close to what "legal review" would confirm. Not resolved here — flagged, per this plan's own convention for founder-only decisions.

**v5 addendum — buddy-system and DAN reference:** see Core Architecture pillar above; not re-litigating platform reliability, only the underlying safety *model*.

### 2. Funding & cost model (resolves `THREAT_MODEL.md` §0.2)
Unchanged: no SMS spend in v1, Vercel/Supabase free tiers, webcam vision-AI free/cheap-tier only with a hard volume cap, priority order (SMS first, then better vision-AI) once budget exists.

**v5 addendum — a ceiling for core infra, not just webcam AI.** `THREAT_MODEL.md` §0.2 asked for a cost ceiling covering *all* infra-heavy features (vision extraction, webcam ingestion, map tiles, CDN'd offline bundles) — only webcam AI actually got one. Two real, currently-unaddressed risks in the other direction too: Supabase free-tier projects **pause after inactivity** (a quiet period could silently take the whole app, including Safe-Return's backend, offline with no monitoring), and Vercel's free "Hobby" tier terms are scoped to personal/non-commercial projects — this app, while unmonetized, is a public multi-user platform with community contribution and moderation, which may not fit that scoping regardless of money changing hands. Flagged for founder decision, not resolved: set an explicit trigger (e.g. "at 80% of any free-tier limit, or any sign of inactivity-pause risk, founder gets an alert and makes an explicit go/no-go on paying"), and confirm actual usage against Vercel's Hobby ToS before real growth makes it a live question.

**v5 addendum — moderation gap is also a cost-abuse vector.** Because any signed-in user (zero vetting — Google sign-up is open to anyone) can approve their own submitted `camera_sources` candidate today (no moderator role modeled yet — see `supabase/README.md` item 6), and every `approved` row becomes eligible for the metered, no-free-tier Anthropic extraction pipeline once `WEBCAM_EXTRACTION_ENABLED=true`, this is a direct path from "create an account" to "spend the project's real money," not just an attribution gap. **Before ever setting `WEBCAM_EXTRACTION_ENABLED=true` in a live environment:** add a minimal moderator/founder-only role for approve/reject, or accept the daily call cap as the explicit worst-case spend the founder has signed off on — don't flip the flag with the current trust model unexamined.

### 4. Security & privacy hygiene — new, resolved 2026-08-08
- **Secret hygiene is now an explicit engineering standard.** A live Google OAuth client-secret JSON sat in the repo root, untracked but **not gitignored**, for this entire build — one `git add -A` from being committed and exposed. Fixed (added to `.gitignore`) the moment this review found it. Standing rule: any credential file downloaded from a third-party console must be gitignored by name/pattern *before* it's saved into the working tree, never left to rely on `.env*`'s existing coverage. Rotate any credential that was ever in an unignored path, even if never actually committed.
- **A public privacy notice is a P0 item, not a later nice-to-have.** The app now performs real Google OAuth sign-in and attributes real activity (`hazard_reports.reported_by`, `lds_status.created_by`, `camera_sources.added_by`/`reviewed_by`) to that identity — confirmed live. There is no privacy policy or terms page anywhere, and no link to one from the sign-in screen. `supabase/README.md`'s data-retention write-up is accurate but internal-only. Required before onboarding real users beyond founder testing: a short, plain-language privacy page (what's collected via Google sign-in, what's stored, how long, how to request deletion) linked from `/login`.
- **P0-C's PII surface description is stale.** In addition to account identity, dive-plan location (not yet built), and local-only timer state, the real v1 PII surface as-built also includes identity-linked attribution on every community submission and moderation action across `hazard_reports`/`lds_status`/`camera_sources` — the same category of risk `THREAT_MODEL.md` §11 flags for a future emergency-contacts feature (pattern-of-life exposure: "this account dives here every Saturday"), smaller in scope but real and live today.
- **Admin/moderation routes rely on obscurity, not access control.** `/moderation/camera-sources` and `/webcam-discovery` gate on "signed in," not "is a moderator" — honestly disclosed on-page (`SecurityGapNotice`), not relitigated here. But there's no `noindex`, no `robots.txt`, and any newly-signed-up stranger who finds the URL (trivial — it's in this repo's own history and task tracker) can act on it immediately. Accepted for v1 given no real user base yet; **must be resolved (a real moderator-role column + route gate, or at minimum `noindex` + a visible "not yet public" banner) before any real invite or launch**, and specifically **before actively soliciting shop-submitted camera sources** (see Task 16's partnership addendum) — a partner staking business reputation on the outcome is a materially worse case than an anonymous community typo.

### 5. Dive Plan — new, minimum viable definition (was previously undefined)
`plan.md` referenced "a user's active dive plan" throughout Tasks 12/14/16 without ever specifying it — three separate implementers independently invented three different stand-ins (`DivePlanCheckInState`, mock pre-trip-checklist dates, the Safe-Return timer's own status as a proxy) because no shared spec existed. Minimum viable definition for **Task 11.5** (new, Phase 1, blocking real Task 12/14 completion): a dive plan is a lightweight record of {site(s), planned date/window, optional "diving with" label (see the buddy-system note above), status (planned/active/completed)}. Created from the (also new, see Map pillar) site detail page. Distinct from but linked to a Safe-Return timer session — starting a timer can optionally attach to an active dive plan, but a dive plan doesn't require starting a timer. Until this exists, Task 12/14's `[x]` status should be read as "done against a stub."

### 6. External dive-site data sourcing — new, resolved 2026-08-08 (founder-directed)
Fixing the map's California-only default (v5.1, see Priority Triage addendum below) surfaced the deeper gap it was a symptom of: `sites` had exactly 3 founder-seeded rows and **no insert path at all**, for anyone, founder or community. The founder proposed three categories of external source and asked for an implementation, prefaced with "fan out and implement, but update the plan and traceability first." Each option was independently fact-checked (not taken on faith) before deciding:

- **"The Dive API" / RapidAPI "World Scuba Diving Sites API"** (~15-17k sites globally, commercial) — its actual free-tier limits could not be confirmed even after direct lookups (RapidAPI's pricing tab is JS-rendered, opaque to automated fetch). Per CLAUDE.md's "no paid dependency without checking the funding model" standard, a dependency whose cost can't be confirmed free is treated as paid until proven otherwise. **Not used. Blocked pending the founder personally checking RapidAPI's pricing tab and confirming an acceptable tier** (see Priority Triage below).
- **`dulcetgnome/divestop`** (GitHub) — real, active repo (Node/Redis/Postgres, a real `/api/sites` endpoint), but **declares no license**. On GitHub, no license means all-rights-reserved by default — not legally reusable without asking the author. **Not used, not blocked-pending-review — this one needs the author's explicit permission to use at all, a different kind of blocker than a pricing check.**
- **`cetra3/divedb`** (GitHub; the founder's pasted link was malformed/duplicated — the real repo was independently located) — real, active project (Rust/actix-web + SvelteKit, live at divedb.net), but licensed **AGPL-3.0**. AGPL's copyleft is network-triggered: vendoring DiveDB's *code* into this app would obligate releasing this app's own source under AGPL too. **Its code is not used.** Whether DiveDB's *data* could be reused separately from its code (e.g. via a public API, if one exists) was not established in this pass — a distinct, open question, not resolved here.
- **OpenStreetMap via the Overpass API** — already researched in depth the same day (see `supabase/sources/dive-site-data-source-options.md`): free, a real `sport=scuba_diving`/`scuba_diving:entry=shore` tagging convention, live-confirmed Florida coverage (34 real nodes on a test query), known ODbL license terms (attribution required; a stored/redistributed derivative database must itself be ODbL, which shapes how imported rows are described in-app). Coverage has real gaps (a Blue Heron Bridge query returned zero results) — this is a starting source to layer community submissions on top of, not a complete one. **Selected as the implementation path** — the only option with both zero cost and fully-known licensing terms.

**Resulting architecture (Task 21, below), matching the founder's own framing ("if searching a new location with no data, use the API"):** an on-demand, cache-then-serve pattern. Local `sites` data is always queried and shown first. When a search radius has few/no local results, an Overpass query runs for that area, results are normalized and upserted into `sites` as **`COMMUNITY`** provenance (automated ingestion is not a moderated human vouching for a row — the existing "no unmoderated write path to `VERIFIED`" standard applies here exactly as it does to any other self-service write) with `legal_access_status` left `null` ("not yet assessed") unless a tag reliably says otherwise, then local data is re-queried and returned. This is explicitly **not** a live proxy to Overpass on every request — imported rows persist in `sites` so the next diver searching the same area gets an instant local read, and a per-area cache/cooldown prevents hammering the public Overpass instance (its fair-use policy is real, not a formality).

**Amended same day (2026-08-08) — cache duration corrected from 24h to ~monthly.** The first pass of this spec used a 24h-per-area cooldown before allowing a re-query of the same area. The founder correctly pointed out this doesn't match the actual data: physical dive site *locations* don't change day-to-day (a reef doesn't move), so a 24h TTL just means re-hitting Overpass for the same area every single day with almost certainly identical results — wasted calls against a fair-use-limited public API, for zero real freshness benefit. Corrected policy: once an area has been searched externally, treat it as durably cached — **do not re-query Overpass for that area again until ~30 days have passed.** This is a data-freshness tradeoff, not a laziness shortcut: a monthly cadence is frequent enough to pick up newly-tagged OSM sites without meaningfully lagging reality, and honest staleness disclosure (this codebase's established pattern — `FreshnessBadge`, "cached as of [time]," never a bare binary badge) is the right tool if a diver wants to know how current an imported site's data is, not a tighter automatic re-fetch cadence. **This corrects Task 21's `T21.3` spec below before any code implementing the old 24h number has been verified/merged** — see `TASKS.md` for current implementation status.

### 7. Site-type classification for map icons — new, resolved 2026-08-08 (founder-directed)
The map currently distinguishes sites only by provenance (ring), hazard-report presence (fill color), and legal-access severity (corner glyph) — nothing about *what kind* of site it is. The founder's ask: shipwreck, shore reef, or "whatever else is a meaningful classification" should render as a distinct icon so the map communicates site type at a glance, not just after tapping through to the detail page.

**Classification source:** OpenStreetMap already carries this signal on the exact nodes Task 21 imports — `historic=wreck` (shipwreck), `natural=reef` (reef), `natural=cave_entrance` (cave/cavern), and Florida-specific, confirmed live in the same-day Overpass research (`supabase/sources/dive-site-data-source-options.md`): a meaningful share of Florida's `sport=scuba_diving` nodes are freshwater springs, a real and distinct local category. Proposed `site_type` enum: `shore_reef` | `shipwreck` | `cave` | `spring` | `artificial_reef` | `unclassified`. `unclassified` is the honest default for the 3 founder-seeded rows and any future manually-added site without a clear category — never guess a type OSM data doesn't actually support, same "don't fabricate what a source doesn't say" discipline the rest of this spec holds elsewhere.

**Open design question, not resolved here:** the map pin already carries three visual dimensions (ring pattern = provenance, fill color = hazard presence, corner glyph = legal-access severity) — the same-day legibility fix (`T11.5.8`... actually `T11.5`'s pin rework) already had to simplify *away* from a hue-coded system because it was unreadable at real pin size. Adding a fourth dimension (site-type icon) risks recreating that exact problem if bolted on carelessly. This needs an actual design pass before implementation — likely the site-type icon becomes the pin's base silhouette/glyph (replacing the generic teardrop shape) with the other three dimensions carried by ring/fill/corner-badge as already established, but that's a proposal, not a spec — resolve it through the same aesthetic-review process (`creative/AESTHETIC_REVIEW.md`) used for the original pin legibility fix before writing icon code, not as an engineering-only decision.

### 8. Map and nearby-sites list share one radius-driven data source — new, resolved 2026-08-08 (founder-directed)
Today `SiteMap` and `NearbyDiveSitesList` are independent siblings in `src/app/page.tsx`: the map renders every site ever fetched server-side, unfiltered by radius; the list (as of `T21.4`) filters/fetches by the radius the diver picks. The founder's ask, correctly identified as a real gap: changing the radius dropdown should update **both** — right now only the list responds. **Resolved architecture (not yet built):** lift shared state (resolved geolocation, selected radius, the current `search-nearby` result set) out of `NearbyDiveSitesList` and into a new client-side wrapper component that owns it once and renders both `SiteMap` and `NearbyDiveSitesList` as children fed from the same data, replacing today's two-independent-siblings structure. `page.tsx` stays a Server Component doing the initial full-list fetch (unchanged, still the SSR fallback/initial-paint content); the new wrapper is what goes client-side and reactive to radius changes. Map re-centering on the diver's real location is **already implemented and live** (`T11.5.8`, `use-geolocation.ts` + `site-map.tsx`'s `flyTo`) — this decision is only about making the map's *rendered pin set* radius-reactive to match the list, not about re-adding location-centering, which already works.

### 9. Map-pin rendering: migrate from one React `<Marker>` per site to a GeoJSON source + symbol layer — new, resolved 2026-08-08 (founder-directed)
`site-map.tsx` currently renders one `<Marker>` (a real DOM element, positioned/repositioned by react-map-gl on every pan/zoom) per row in `siteMarkers`. That's fine at 3 sites; it visibly degrades well before "hundreds or thousands," which is now a realistic near-term number once Task 21's OSM pipeline is actually populating `sites` at scale, not a hypothetical. The founder correctly flagged Mapbox's own recommended pattern for this: a GeoJSON `Source` (one feature per site, coordinates + properties like provenance/`site_type`/`hasHazardReport`/`legal_access_status`) rendered via a `symbol` `Layer` with `map.loadImage()`-loaded custom icons, all composited on the WebGL canvas instead of the DOM — this is the standard, correct answer for marker counts at this scale, not a premature optimization.

**Resolved approach (not yet built):** migrate `site-map.tsx`'s site-pin rendering (the LDS/fill-station dots stay as-is — that layer is small and mock-data-driven, not the one about to scale) to react-map-gl's own declarative `<Source>`/`<Layer>` components, which wrap exactly this Mapbox pattern — **not** raw imperative `map.addLayer()` calls, to stay consistent with how the rest of this component is already written (declarative React, not an escape hatch into the imperative Mapbox GL JS API). Practical implications worth planning around now rather than discovering mid-implementation:
- **This is the natural, correct foundation for `T21.5` (site-type icons) and `T21.6` (radius-reactive map), not a separate concern layered on top of them** — a symbol layer's `icon-image` can be a *data-driven expression* keyed directly on each feature's `site_type` property (one layer, many icons, no per-type React component branching), and radius-filtering becomes a `setData()` call or a layer `filter` expression on the existing source instead of React reconciling a changed array of `<Marker>` components. Sequencing these three as one combined rendering-architecture pass (rather than building `<Marker>`-based type icons now and re-migrating to symbol layers later) avoids throwaway work.
- **Interaction handling changes.** `<Marker>`'s per-site `onClick`/`<Link>` wrapping (`SitePinMarker`'s current approach) doesn't exist on a symbol layer — clicks are handled via `map.on('click', layerId, handler)` and `map.queryRenderedFeatures()`, reading the clicked feature's properties (including its `id`) to navigate to `/sites/${id}`. The existing hover/cursor affordance (`cursor-pointer`) becomes a `mouseenter`/`mouseleave` pair setting `map.getCanvas().style.cursor`.
- **Icon assets**: custom icons need to be loaded once via `map.loadImage()`/`map.addImage()` before the layer references them by name — plan for a small sprite-like set of PNG/SVG icons per `site_type` (ties directly into `T21.5`'s still-open design-pass requirement; the icon *assets* this decision needs are the same ones that design pass needs to produce either way).
- **Accessibility regression to solve, not ignore:** the current `<Marker>` approach gets a real DOM element with `aria-label`/`title` "for free" (see `SitePinMarker`'s existing `label`/`title` props). A symbol layer has no DOM node to attach that to — screen-reader accessibility for map pins needs a deliberate answer in the migration (e.g. a synchronized off-canvas/visually-hidden list of visible sites, which `NearbyDiveSitesList` may already substantially provide) rather than silently regressing accessibility in the name of performance.
